    Where a mistake gets caught
    
        
    
          The same broken path can surface at three different moments. The earlier it does, the
          cheaper it is to fix — so fhirpath-ts pushes as many checks as it can up toward the
          keystroke, and leaves as little as possible for production.
        
    

        
    
          
    
            As you type
            tsc · no plugin
            
    Type error
    
          
    
          
    
            
    const given = r4.compile('Patient.name.given')   // string[]

given.evaluate(observation)             // won't compile: expects a Patient
given.evaluate(patient)[0].toFixed(1)   // won't compile: it's a string
    
            
    
              The input and result types are inferred straight from the expression literal, in plain
              TypeScript. Pass the wrong resource, or misuse the result, and your editor flags it
              before you save. It's the narrowest net — expressions outside the supported subset fall
              back to unknown[] rather than a false error — but it costs nothing to run.
            
    
          
    
        
    

        
    
          
    
            Before you run
            fhirpath-check · ESLint · in CI
            
    Static analysis error
    
          
    
          
    
            
    analyzeExpression('Observation.valueQuantity', opts)
// Element 'valueQuantity' is not defined on FHIR.Observation

analyzeExpression('Patient.name.given.substring(1)', opts)
// substring() expects a collection with a single item as input (spec §11)
    
            
    
              Typos, choice-key misuse, singleton misuse, equality that can never hold — the whole
              class TypeScript's type system can't express. The §11 analyzer reads the expression
              against the FHIR model and reports them without touching data. It ships two ways to run:
              fhirpath-check, a CLI that scans your .ts/.js files
              for FHIRPath literals (tags, compile(), evaluate()) and exits
              non-zero on any finding — drop it into a CI step; and
              fhirpath/no-invalid-expressions, an ESLint flat-config rule that flags the
              same literals inline in your editor and fails eslint. This is the layer the
              playground above runs live.
            
    
          
    
        
    

        
    
          
    
            Only when it runs
            against real data
            
    Runtime error
    
          
    
          
    
            
    r4.evaluate('Patient.namee.given', patient)   // []  — no error, just empty
    
            
    
              This is what the two checks above exist to shrink. Against real data most mistakes
              don't throw — an unknown path just returns nothing, and you learn about it from a failing
              test or a blank field, not an exception. A few hard cases genuinely throw (choice-key
              misuse, an unconvertible unit), but the silent empty result is the one that reaches
              production, which is why fhirpath-ts turns as much of it as it can into the two errors
              you can catch first.
